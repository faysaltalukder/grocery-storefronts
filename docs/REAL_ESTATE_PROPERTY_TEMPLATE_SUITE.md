## Image allocation and ownership

The page-level rule is enforced for each template:

- Homepage: exactly 5 meaningful images.
- Every other page: exactly 2 meaningful images (within the required 2–4 range).
- Each 40-page template therefore contains 83 unique image assets: 5 + (39 × 2).
- The four templates contain 332 unique image IDs in total.
- Image IDs are unique across pages and across all four templates.
- Images are original first-party architectural SVG illustrations generated by the storefront runtime's `propertyArtSrc()` function. They are not third-party hotlinks or stock-provider URLs.
- The page renderer uses image links only to valid internal routes through `pageUrl()`. If an image has no useful internal destination, it must remain non-clickable.
- No image links to an external website. No image source in the property page catalog is an external HTTP(S) URL.
- Each image record includes its ID, alt text, scene type, purpose, source, creator, license, attribution, render path and date checked.

The artwork generator varies palette and composition by template, scene and unique image ID. Scene families include residential exteriors, interiors, kitchens, amenity spaces, floor plans, neighbourhood maps, office buildings, retail frontages, development sites, landscapes and accessibility routes. These are original illustrative assets, not photographs of real properties.

## Property information and safety of sample content

All included listing names, locations, price labels, measurements and project descriptions are explicitly illustrative sample content. They are not representations of real inventory, verified property ownership, title, approvals, availability, rent, sale prices, agents or development status.

Before publication, the operator must replace sample information with verified records and confirm:
- property ownership/title, permissions and relevant approvals;
- current prices, rent, availability, fees and lease/sale terms;
- accurate measurements, floor plans, amenities and location details;
- agent names, qualifications, biographies and contact information;
- project stage, construction updates, unit mix and developer claims.

No fictional agent identity, credential, testimonial, review, property transaction or guaranteed return is presented as real.

## Interactions and backend boundaries

- Homepage search sends visitors to the internal property-search page.
- Listing pages provide client-side keyword and property-type filtering over the configured sample/page content.
- Property and project detail pages link to internal viewing and information-request pages.
- Viewing and information forms submit through the existing shared quote/request adapter to `builder.quote_requests`, with `business_type = real-estate-property`.
- A request is not a confirmed viewing, offer, reservation, lease, sale or property transaction. The operator must confirm the next step.
- Online property payments, online unit reservations, lease signing, tenant portals and a dedicated property-listing CRUD module are not included in this template-design implementation. The current preview listings are illustrative page content; a dedicated live property inventory/admin module is a separate backend phase.

## Runtime and QA enforcement

- `admin/neon-builder-api.js` allows only the four registered property template keys and checks that each has exactly 40 active pages.
- It validates five images on the homepage, 2–4 on every inner page, exactly 83 unique IDs per template and rejects external image sources.
- `storefront.js` renders the property-specific homepage, listing/filter, detail, editorial and enquiry experiences, with responsive property navigation and a mobile dock.
- `admin/wordpress-templates.js` registers the four template previews and opens the matching live private storefront preview.
- `admin/website-builder.js` provides each template's own page-editor profile and theme palette.
- The final release must pass the repository's bundle validation and the 40-page/image allocation checks.
