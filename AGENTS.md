# Agent Instructions — WordPress Studio Website Templates

## Mandatory master standard

Before doing any design, content, engineering, template, industry, or website-building work in this repository, read and follow:

- **Canonical standard ID:** `MASTER_WEBSITE_ENGINEERING_STANDARD`
- **Canonical file:** [`docs/MASTER_WEBSITE_ENGINEERING_STANDARD.md`](docs/MASTER_WEBSITE_ENGINEERING_STANDARD.md)
- **Repository identity:** `faysaltalukder/grocery-storefronts`

This is the universal, industry-neutral specification for every industry and every template. It is not limited to grocery despite this repository's historical name.

### Trigger phrases
Treat any of these as an explicit instruction to load and apply the master standard:
- `MASTER_WEBSITE_ENGINEERING_STANDARD`
- `MASTER WEBSITE STANDARD`
- `UNIVERSAL TEMPLATE STANDARD`
- `WEBSITE TEMPLATE MASTER GUIDELINE`
- `docs/MASTER_WEBSITE_ENGINEERING_STANDARD.md`
- `faysaltalukder/grocery-storefronts`

If a user names an industry and asks for four templates, apply the standard to all four. If the user names a template number or name, identify that exact template and apply the standard to it.

## Required execution behavior

1. Read the complete master standard before planning or editing.
2. Inspect the existing code, template inventory, shared runtime, admin, backend/API, database contracts, deployment process, and tests relevant to the task.
3. Identify four distinct business models for each requested industry. Never make four superficial visual variants of one business.
4. Build complete, interactive, content-rich business websites. Do not stop at static previews or homepage mockups.
5. Preserve current architecture and working behavior. Extend shared systems rather than creating incompatible parallel systems.
6. Keep website data isolated by stable website identity while retaining authorized central administration and cross-site order visibility with clear website context.
7. Make routine design, content, asset, and implementation choices autonomously. Do not ask the user to choose fonts, colors, icons, photos, layouts, or other ordinary details.
8. Use free/open assets only after verifying their actual licenses and restrictions; document attribution and source information when required.
9. Do not invent content claims, credentials, reviews, integrations, successful transactions, test results, or deployments.
10. Back up and establish rollback before risky or destructive data/schema changes. Never expose secrets.
11. Test the complete customer journey, admin workflow, tenant isolation, responsive behavior, accessibility, performance, SEO, and existing-template regressions.
12. Do not mark work complete while a critical release blocker remains. Report actual test evidence and any unavailable/live-unverified integration.

## Repository safety

- The repository name does not limit the industries that may be designed here.
- Do not assume the central admin or commerce backend lives in this repository. Read the current README and architecture before changing integration boundaries.
- Keep documentation-only changes separate from runtime changes.
- Do not make destructive production data changes as part of a template task unless explicitly required, backed up, and safely reversible.
- Follow the master standard's quality rubric and release gates.

## Completion response

Summarize what was built, the business model and template identity, pages/content/catalog delivered, working journeys, admin/backend integration, QA evidence, quality score, commit/deployment references, and remaining blockers. Never claim unverified success.
